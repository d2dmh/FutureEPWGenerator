# CMIP6 Remote I/O Resilience v1.2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make Stage 02 robust to slow/broken GCS Zarr assets without changing the scientific interpolation or cache schema.

**Architecture:** Keep GCS as the primary source, derive the documented AWS `cmip6-pds` mirror path as a fallback, and run each provider in its own timeout-bounded worker. For rectilinear grids, preselect only the two latitude and two longitude support coordinates before calling xarray linear interpolation, preserving the v1.1 bilinear method while reducing remote chunk reads. Stream worker stage logs to the terminal and keep cache validation unchanged so v1.1 caches remain reusable.

**Tech Stack:** Python 3.13, pandas, xarray, zarr 2.x, gcsfs, s3fs, cftime, fsspec, pytest.

**Spec:** Conversation-approved v1.2 design: GCS -> AWS fallback, local 2x2 support-window reads, stage-level worker logs, v1.1 cache compatibility.

## Global Constraints
- Do not change CMIP6 model/member/grid/scenario/window selection.
- Do not change morphing formulas or EPW generation logic.
- Keep cache filenames and cache validity schema compatible with v1.1.
- Preserve xarray linear interpolation for rectilinear grids; only reduce the spatial subset supplied to it.
- GCS remains primary; AWS is fallback only.
